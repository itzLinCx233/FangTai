# 个性化膳食规划 Agent · 技术方案文档

> 第二届浙江省大学生人工智能竞赛 · "方太"人工智能专项赛（ZX-2026-0301）
> 发榜单位：宁波方太厨具有限公司

## 1. 方案总览

本系统基于大语言模型（默认 GLM-5.3-flash，思考强度 high）构建个性化健康膳食推荐 Agent，
围绕赛题四项评分要求设计：

| 评分项 | 分值 | 本方案对应设计 |
|---|---|---|
| ① 基础推荐 | 20 | 硬约束引擎（过敏原/忌口映射）+ 候选池前置过滤 + 选菜零幻觉 + 输出后二次校验 |
| ② 复杂场景组合 | 20 | 多人约束交集合并 + 整桌组合优化（荤素比/冷热比/烹饪方式多样性）+ 按人营养核算 |
| ③ 多轮动态交互 | 30 | 会话约束栈（上下文不遗忘）+ 意图分类 + 最小化修改（仅替换违规菜）+ 模糊需求主动澄清 |
| ④ 性能效率 | 30 | 云端 RAG（阿里云百炼嵌入+重排）+ 槽位抽取与检索并行 + SSE 流式输出 + 前导确认句提前首 Token |

### 1.1 总体架构

```
用户消息 ──┬─► 槽位抽取（规则快路径 + LLM JSON 联合抽取，与检索并行）
           └─► 约束状态机（DialogSession：约束栈跨轮持久）
                     │
                     ▼
        硬约束过滤（ConstraintEngine：过敏原→食材别名正则；慢病忌口规则）
                     │  生成候选池 ok_ids（2000→约700-1400）
                     ▼
        混合检索（Retriever：阿里云百炼 RAG，本地 BM25 兜底）
          BM25(jieba, 内存) ⊕ 向量召回(text-embedding-v4, 离线索引) → RRF 融合
          → 标签/偏好加权 → gte-rerank 重排
                     │  Top-N 候选菜谱（ID+名称+食材+标签）
                     ▼
        LLM 选菜（只允许引用候选 ID → 输出 JSON；程序校验存在性=零幻觉）
                     │
                     ▼
        组合校验（Planner：汤数控制/荤素搭配补齐；末次零违反扫描，违规自动替换）
                     │
                     ▼
        营养核算（Nutrition：食材克数×成分表，份额自适应）→ 结构化 plan 事件
                     │
                     ▼
        LLM 流式生成推荐说明（SSE delta）→ 前导确认句 + 每菜理由 + 营养数据引用
```

## 2. 数据设计

### 2.1 菜谱库结构化（recipe_store.py）

原始数据 2000 条 CSV（GB18030 编码），做四层结构化：

1. **标签规范化**：185 个原始标签 → 43 个规范标签（六维：餐次/菜系/口味/节日/人群/功效），
   含同义词归并（湘菜→川湘菜、中秋→中秋节、鲜美→鲜等）与噪声清洗
   （剔除 8 条 LLM 推理文本污染标签、连续分隔符）
2. **食材清单结构化**：解析"主料/辅料/A料/B料"分组、全角分号切分、
   克数正则（g/克/毫升/个/根/片…）、双括号清理，输出 `{name, grams, count, unit, group}`
3. **菜品分类**：按主料克重判定荤/素/蛋/豆制品（供荤素比）；步骤文本命中烹饪方式
   （蒸/烤/炒/炖/煮/拌/煎/炸/榨汁，供多样性）；菜名判定冷/热
4. **烹饪时长估算**：步骤中"N分钟/N小时"求和与最大值折中（供时间约束过滤）

同名菜谱（75 组，如"红烧肉"×3）按不同配方保留多条，检索与选菜以 **数字 ID** 唯一引用。

### 2.2 用户健康档案（profiles.py）

50 份 JSON（基础信息+体检指标+特殊人群+过敏+偏好+需求），加载为 id→profile 字典，
`profile_text()` 生成自然语言描述注入 LLM 提示词。

### 2.3 约束知识库（constraint_engine.py）

- **过敏原映射表**：13 类过敏原（海鲜/虾/蟹/鱼/坚果/花生/牛奶/鸡蛋/豆类/豆制品/芒果/啤酒/酒精）
  → 共 200+ 食材别名（含蚝油/鱼露/虾皮等隐性来源，长别名优先匹配）
- **慢病/人群忌口表**：高血糖（糖类主料）、高血压（腌制品）、高尿酸/痛风（贝类/内脏/浓汤/啤酒/香菇）、
  孕妇（酒精/生食/山楂/薏米）、哺乳期（麦芽/韭菜回奶）、备孕（酒精/咖啡因）
- **健康需求关键词表**：60+ 需求（增肌/补钙/补铁/催乳/降尿酸…）→ 食材与功效标签（检索软加权）

## 3. 检索策略（RAG）

### 3.1 混合检索流水线

```
查询 → jieba 分词 BM25（词法精确命中：菜名/食材名）
      → bge 向量召回（语义：家常/清淡/养胃/减脂餐 等自然语言）
      → RRF 倒数排名融合（K=60，各取 Top-180）
      → 软偏好加权（健康需求食材/功效标签/口味命中 +0.02/次）
      → 标签过滤（餐次硬过滤，不足自动放宽）
      → bge-reranker GPU 重排（Top-24 对，截断文本+fp16，单次 ~150ms）
```

### 3.2 云端 RAG（阿里云百炼）+ 本地 BM25 兜底

- **嵌入**：百炼 `text-embedding-v4`（OpenAI 兼容端点，1024 维，10 条/批），
  2000 条菜谱向量**离线预计算**并缓存（`scripts/build_index.py`，约 200 次 API 调用），
  查询实时编码（单条调用）
- **重排**：百炼 `gte-rerank`（原生端点），Top-24 候选单次调用
- **BM25 本地内存索引**始终保留：云 API 失败/超时自动降级纯 BM25，服务不中断
- **检索质量与延迟**：本地 GPU 模式实测平均 124ms；云端模式增加约 300-600ms API 往返，
  换取零 GPU 依赖与轻量部署（Docker 镜像从 CUDA 版降至 python slim）
- **可切本地 GPU 模式**：`RAG_PROVIDER=local`（bge 系列常驻显存），适配无外网评测环境

### 3.3 零幻觉保障（评分①"菜谱真实性"）

- LLM 选菜提示词**只提供候选列表**（ID+名称+食材+标签），要求输出 `{"id":...}` JSON
- 程序校验：ID ∉ 候选池 → 丢弃；选不出 → 回退规则组合（planner 直接从检索池构造）
- `eval.py` 对每轮输出做菜谱存在性校验（按 ID 与名称双查 2000 条库）

## 4. 多约束推理（评分①②）

### 4.1 双遍校验（零违反）

```
第一遍（前置）：ConstraintEngine.banned_pattern 编译全部违禁词（过敏+忌口+会话追加）
              → store.filter_ids() 生成 ok_ids 候选池 → 检索只在该池内进行
第二遍（兜底）：LLM 选出菜品后逐道 constraints.ok() 扫描（食材级关键词匹配）
              → 违规自动用池中合规菜品替换 → finalize_plan 末次全量扫描
```

实测（20 用例回归）：**过敏/忌口违反 0，幻觉菜名 0**（见评测报告）。

### 4.2 多人宴请（评分②）

- 多档案 `merge_constraints()`：违禁取**并集**（任何人的过敏原对整桌生效），健康需求保留并集
- 整桌组合优化（planner.py）：
  - 菜数规则：2人2菜 → 6人5菜（宴请人数+1），支持"四菜一汤"显式约束
  - **汤先行**：优先 1 道汤（汤品模式识别：名称含汤/羹/煲 或 炖煮类）
  - **荤素比**：荤:素 ≈ 6:4，豆制品/蛋类计入素方向
  - **烹饪方式多样性**：素菜挑选时优先未出现过的做法，目标 ≥3 种
  - **冷热比**：冷菜 ≤ max(1, 菜数/4)
- **按人营养核算**：食材克数 × 精简食物成分表（150+ 常见食材，参考《中国食物成分表》，
  含嘌呤列）→ 热量/蛋白/脂肪/碳水/嘌呤级别；**份额自适应**（大锅菜按体量折算份数，
  避免整锅汤按 2 人计导致营养高估）；输出相对劳动强度目标的偏差报告

## 5. 多轮动态交互（评分③）

### 5.1 会话状态机（dialog.py）

```
DialogSession = {
  profile_ids,                    # 档案（跨轮持久）
  constraints,                    # 约束栈：档案约束 + 每轮追加（忌口只增不减 → 上下文不遗忘）
  current_plan[{id,name,role,locked}],   # 当前方案，locked=用户已确认
  meal/people/time_limit/dish_count,     # 槽位状态
  history                         # 对话历史
}
```

### 5.2 意图与槽位联合抽取

- **规则快路径**（0ms）：首轮简单请求（"今晚吃啥"类）正则直达 new_request，跳过 LLM
- **LLM 抽取**（多轮/复杂）：一次 JSON 调用联合输出 8 类意图 + 10 个槽位
  （餐次/人数/时限/菜数/汤/新增忌口/正向口味/主题词/是否模糊/澄清问句）
- 六类交互场景的处理策略：
  - **约束追加**（"别做辣的"）→ 入约束栈；当前方案零违规则**保持不变并说明**（最小化修改）
  - **局部替换**（"把汤换掉"）→ 仅重检索被点名/违规菜品，其余 locked 保留
  - **方案否定**（"都不要"）→ 清空方案重规划，但**保留约束栈**
  - **模糊追问**（"有仪式感"）→ 无档案约束时主动澄清（clarify 事件），有档案则按档案直推
  - **需求矛盾**（"一人要辣一人不碰辣"）→ 抽取阶段标记 add_constraint，选菜阶段折中
    （如以姜/蒜提味替代辣椒，主辣辅清淡双菜并行）
  - **上下文回溯** → 会话状态查询接口 `GET /api/sessions/{sid}` 可审查全部约束与方案

### 5.3 最小化修改原则

新增约束后 `violating_dishes()` 仅标记两类菜品：①命中违禁词 ②超出新增时限。
其余菜品 locked=True 保留，说明文案中显式标注"沿用上轮"及保留原因。

## 6. 性能设计（评分④）

| 手段 | 效果 |
|---|---|
| 嵌入索引离线预计算 + 常驻显存 | 查询编码 ~16ms，无冷启动 |
| BM25 内存索引 + RRF 向量化融合 | 全检索路径 ~124ms（实测） |
| 槽位抽取 ∥ 粗检索 并行（asyncio + to_thread） | 首轮 LLM 延迟与检索重叠 |
| 规则快路径（简单首轮免 LLM 抽取） | 意图理解 0ms |
| SSE 流式 + 前导确认句（槽位解析完即输出） | 首 Token ≈ 槽位抽取耗时 |
| 结构化 plan 事件先于正文流 | 评测方可提前拿到可校验方案 |
| 思考强度可配（LLM_THINKING） | high 保质量 / low 保速度，一键切换 |

> 说明：当前按"质量优先"配置思考强度 high（用户要求），延迟数据为该配置下的实测；
> 切换 low/disabled 可显著降低首 Token 与端到端耗时（评测脚本可复测）。

## 7. Harness 工程实践（评测对齐）

`scripts/eval.py` 实现与赛题验收口径一致的自动评测：

- **用例驱动**：20 组官方对话用例 × 分配 20 份不同档案（覆盖孕妇/三高/过敏/增肌/备孕等）
- **指标采集**（HTTP SSE 口径）：首 Token（首个 delta）、单轮端到端、多轮平均（按用例）
- **正确性校验**：
  - 过敏/忌口违反：对每道输出菜做约束引擎复检（每轮）
  - 菜谱存在性：ID+名称双查库，统计幻觉数
  - 零违反通过率 = 无违反且无幻觉的轮次占比
- **评级**：按赛题优秀/合格阈值（2s/5s、8s/15s、6s/12s）自动评档
- 输出 `eval_report.json`（逐轮明细 + 汇总），`--case N` 支持单用例调试

单元测试 `tests/test_core.py` 覆盖：标签规范化/食材解析/存在性、过敏与忌口判定、
多人合并、营养估算合理性、组合规划多样性、规则槽位抽取（时间/人数/菜数/意图）。

## 8. 创新点

1. **零幻觉选菜协议**：候选 ID 限定 + 程序存在性校验 + 规则回退三层保障，杜绝编造菜名
2. **约束即正则**：过敏原/忌口编译为单一正则的候选池前置过滤 + 输出后扫描，双遍零违反
3. **份额自适应营养核算**：按菜品总克重自动折算份数，按人输出营养与劳动强度目标的偏差
4. **多档 GPU 推理配置**：A100-80G（bge-m3+大重排）/ 12G（bge-large+轻量重排）一键切换
5. **思考格式自动探测**：LLM 层对 GLM-4.5/5.x 的 thinking/reasoning_effort 参数差异
   自动探测缓存，跨 provider 无感切换
6. **结构化 plan 事件流**：SSE 中先发机器可校验的方案 JSON，再流式输出说明，
   兼顾自动评分与人工体验

## 9. 前后端框架与数据层（工程化升级）

- 前端：**Vue 3 + Vite + TypeScript**（vue-router 路由 / Pinia 状态 / Element Plus 后台组件库），
  聊天页与管理后台组件化；SSE 解析、用户中心等交互逻辑与旧版一致
- 后端数据层：**SQLAlchemy 2.0 ORM**（声明式模型 + 连接池），DAO 对外签名不变，业务路由零改动
- 数据库演进：**Alembic** 版本化迁移（基线 0001_initial，启动自动 stamp；
  后续改表用 `alembic revision --autogenerate` + `alembic upgrade head`）
- 兼容设计：FastAPI 优先托管 frontend/dist；无 Node 构建环境回退 app/web 旧静态页，
  评测机直接可用
